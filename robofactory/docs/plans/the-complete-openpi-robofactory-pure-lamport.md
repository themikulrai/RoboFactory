## Glossary (so the bytes table makes sense)

- **Sim trajectory zarr/h5**: pre-computed simulation rollouts. Each "trajectory" is a sequence of `(observation, action, next_observation, reward, done)` tuples generated by the simulator (SAPIEN/Maniskill) under a scripted/teleoperated policy. Stored as zarr arrays (efficient chunked NumPy) or HDF5 (legacy). These are the **training data** for DP and Pi0.5 — they don't get regenerated unless the underlying scene/task changes. ~363 G in `data/RoboFactory/{zarr_data,h5_data}`.
- **HF model weights** (92 G in `.cache/huggingface`): pretrained weight blobs downloaded by `huggingface_hub`. In this project: Pi0.5 base weights (`paligemma-3b-pt-224` family ≈ 3 G), Gemma text-encoder, DINOv2-small (~150 M), DINOv2-base (~350 M), R3M (~50 M), CLIP variants, possibly LIBERO datasets. Re-downloadable. The reason it's 92 G is repeated downloads of similar checkpoints + LIBERO sim data versions cached here.
- **Two dataset formats — RLDS and LeRobot — why both?**
  - **LeRobot** (parquet + arrow, HuggingFace-native): the canonical format for openpi/Pi0.5 *finetune training*. Efficient random access, integrates with HF Hub, fast iteration on a single machine. **All your RoboFactory data is converted into this** via `examples/robofactory/convert_robofactory_data_to_lerobot.py`.
  - **RLDS** (TFRecord-based, Google's Robotics Datasets format): what the OpenX-Embodiment / RT-2 / RT-X corpus ships as. **Pi0.5's base model was pretrained on RLDS**, so finetune codepaths still support reading RLDS directly when you want to mix in pretrain-style data without reconverting. LIBERO is published in both formats.
  - **Why keep both code paths**: pretrain-mix finetuning loads RLDS; pure RoboFactory training loads LeRobot. Removing RLDS support breaks the "warmstart from pretrain mix" workflow you might want for the harder tasks (TSC, LP). Removing LeRobot support breaks the canonical training pipeline.
- **Wandb local cache** (268 M in `projects/openpi/wandb`): one subdir per run as `run-YYYYMMDD_HHMMSS-<runid>/`. Contains: media files (videos), staged metric blobs awaiting sync, run config dumps. **Only ~50% of these are useful** — once a run has synced cleanly to wandb cloud, the local subdir is purely a copy. Crashed runs, debug runs, and runs that started + immediately died leave behind subdirs that are never useful.
- **Logs unrelated to main runs**: yes, you're right — the eval/training/debug log subdirs are independent buckets. `eval_pi05_decent/` is the Pi0.5 decent-eval JSON dumps, `eval_pi05/` is centralized Pi0.5 evals, `phase2_debug/` is LIBERO ablation phase-2 debug dumps (preserve), `eval_bisection/` is the bisection one-off (junk), `RoboFactory/` is RoboFactory training logs (mostly DP). They can be triaged independently.

### Why is `src/openpi/training/config.py` so big? (+163 new lines)

Pi0.5 introduces several new training axes that didn't exist in the openpi base, each requiring its own config dataclass:

1. **`LoraConfig`** — adds LoRA-specific knobs (rank, alpha, dropout, `target_modules` regex). LoRA replaces full-finetune for the Gemma text encoder + image projector layers; without this dataclass there's no way to express "rank 16 on attention only" at the config layer.
2. **`FreezeConfig`** — phase-aware freeze schedules. Pi0.5's training has multiple phases (e.g. phase 1 freezes vision, phase 2 unfreezes). This config lets you say "freeze layers matching `*.encoder.*` for steps 0–10000, then unfreeze."
3. **`UniformTWeightedConfig`** (you asked about this) — the diffusion training loss weights samples by the noise timestep `t`. The default schedule (uniform over `t ∈ [0, T]`) is fine for unconditioned diffusion but wastes capacity on already-easy timesteps when finetuning. `UniformTWeightedConfig` lets you bias sampling toward middle-t (where most signal lives) or toward edge-t (where the policy is most action-relevant). Concretely, it parameterizes a piecewise-linear weight `w(t)` and the loss becomes `E[w(t) · ‖ε̂ − ε‖²]` instead of plain MSE. Useful when finetune compute is short and you want the loss optimization to focus on timesteps that change downstream rollout success the most.
4. **`DataConfig.suite_filter`** — LIBERO has 4 task suites (spatial/object/goal/long); this lets training read only one suite from a unified dataset blob.
5. **`DataConfig.rlds_data_dir`** — RLDS-format datasets (Google's robotics format) live at a different path than LeRobot-format data; this adds the second loader.

All five are new dataclasses with field documentation, validators, and `__post_init__` checks. That's how you reach +163 lines without bloat.

**Can config.py itself be parameterized to remove clutter? Yes.** The +163 LOC of *dataclasses* (the schema) stays — those are the type-safe knobs. What's actually cluttering is the **per-config registrations** elsewhere in the codebase: separate `pi05_robofactory_pm_lora_finetune`, `pi05_pm_wristcam_v1`, `pi05_robofactory_decent_lora_finetune_arm0/1/2`, `pi05_robofactory_decent_wristcam_lora_finetune_arm0/1/2`, etc. That's ~10+ near-identical config entries differing only in `(dataset, task, scheme, arm)`.

Concrete cleanup (Phase C, additional commit):

1. Introduce **one template** `configs/pi05/robofactory_template.yaml` containing all the shared knobs (LR schedule, LoRA rank, freeze schedule, validation cadence, t-weighting).
2. Introduce a **factory function** `make_robofactory_config(model, dataset, task, scheme, arm=None) -> TrainConfig` in `src/openpi/training/config_factory.py` that:
   - reads the template
   - derives `data.zarr_path` / `data.lerobot_path` from `(dataset, task)`
   - derives `model.num_arms` and the LoRA target-module pattern from `scheme` (cent vs decent)
   - derives `model.checkpoint_save_path` from the canonical `run_id`
   - sets `data.suite_filter` to match `task`
3. Delete the per-(dataset, task, scheme, arm) config registrations once the factory is wired into the launchers.
4. Same factory pattern for DP configs: `make_robofactory_dp_config(...)`.

After this, "add a new task" = add 1 row to `matrix.csv` + author 1 task config (the env spec); no new training-config registration needed. "Add a new dataset variant" = same. Cuts ~10 config files down to 2 templates.

### `restore_params_only()` — when do you need this?

**Yes, this is finetuning-specific.** Use cases:

- **Phase change in Pi0.5 training**: phase-1 trains with one optimizer state (e.g. higher LR, no weight decay, certain layers frozen). Phase-2 needs a fresh optimizer because the LR schedule restarts and the freeze mask changes. You want the model weights from end-of-phase-1, but the optimizer's running moments and LR schedule from phase-1 are now meaningless.
- **Resuming from a base checkpoint with a different optimizer setup** — e.g. you finetune from `pi05_base.ckpt` but want to use AdamW with a custom LoRA-decay mask (which the base ckpt's optimizer state doesn't have).
- **Cross-task warmstart**: take PM ckpt, finetune on TSC. Optimizer state from PM is useless on TSC.

In all three, `restore_params_only(ckpt_path)` loads only the model state dict and discards optimizer/scheduler. Without it, you'd either re-init from scratch or carry over stale optimizer moments that fight the new schedule.

## The runs matrix — note on centralized vs decentralized

You're right that I missed this dimension. **Multi-arm tasks (2SC, TSC, LP) have two control schemes:**

- **Centralized**: one model controls all arms (joint training/inference). Naming pattern `*_joint_*`. Example ckpt dir `ThreeRobotsStackCube-rf_joint_d1_workspace_150`.
- **Decentralized**: separate model per arm; each arm trains on its own observation/action slice. Naming pattern `*_agent{0,1,2}_*` for DP, `*_decent_lora_finetune_arm{0,1,2}_*` for Pi0.5. At eval, three policy servers run in parallel and a coordinator routes per-arm action queries.

**Single-arm tasks (PM)** have only centralized.

So the *full* future matrix has cent + decent dimensions, doubling the multi-arm count. This is **kept in context only** — I'm not setting it up here. The reason it matters now is: the new naming convention, manifest schema, and SLURM templates all need to *accommodate* cent/decent so that when you're ready to run them, no schema migration is needed.

- **Cross-run checkpoint clobber (CRITICAL — silent loss of training compute)**: BOTH model stacks have a flavor of this bug.
  - **DP**: `policy/Diffusion-Policy/diffusion_policy/workspace/robotworkspace.py:381` saves to `checkpoints/{zarr_stem}/{epoch+1}.ckpt`. The path is keyed only by zarr stem and epoch — NOT by run id, encoder, or git sha. Any two runs sharing a zarr stem (e.g. encoder-fix `dn5uqhrs` + original `mt4qzgll` both training on `_agent0_d2_wristcam_150.zarr`) write into the same directory; each save can silently overwrite an earlier run's same-epoch ckpt and a later resume can load encoder-incompatible weights. This is what made the 2026-05-04 "empty checkpoint dirs" panic look real until a deeper search proved the dirs were full — just shared.
  - **Pi0.5 (openpi)**: same family, different mechanism. `checkpoint_dir = $OPENPI_DATA_HOME/<config_name>/<exp_name>/` is keyed only on `(config, exp_name)`. Passing `--overwrite` to `scripts/train.py` calls `shutil.rmtree(checkpoint_dir)` at startup, which **deletes any prior run's ckpts that happen to share the same exp_name**. Concrete loss: `v7fldf8d` ran with `--overwrite` and wiped `fuktr1yw`'s 18000-step ckpt — ~14 GPU-hours of compute disappeared. The user only had `fuktr1yw` to fall back on if the next attempt failed; instead they got a fresh-from-scratch retry (`o8atbues`) because the predecessor's ckpt no longer existed.
  - **Action**: dispatch a subagent to:
    1. Change DP save path to `<output_dir>/checkpoints/<run_id>/<epoch>.ckpt` (per-run dir; no cross-run collision).
    2. Change Pi0.5 `checkpoint_dir` to embed `wandb_run_id`: `$OPENPI_DATA_HOME/<config_name>/<exp_name>/<wandb_run_id>/`. New runs always get a fresh dir; resume reads the previous run's `wandb_run_id` from a manifest pointer.

## Naming convention (improved across the board)

### Canonical `run_id` format

**Train run_id**: `<model>_<dataset>_<task>_<encoder>_<scheme>[_arm<N>]_train_s<seed>_<git7>`
**Eval run_id**: `<model>_<dataset>_<task>_<encoder>_<scheme>[_arm<N>]_eval_c<ckpt>_s<seed>_<git7>`

The asymmetry is deliberate:

- **Train run_id has no step**. The train run is a single logical entity that evolves over time. If we embedded the step, every resume would change the dirname and create a fresh wandb run — which is exactly the bug you flagged. The current step lives in `run_meta.yaml` and updates in place.
- **Eval run_id embeds `c<ckpt>`**. Eval is single-shot; you want to know which ckpt step was eval'd at a glance.

Tags (fixed order so run_ids sort cleanly):

- `model`: `dp` | `pi05`
- `dataset`: `ws` (workspace cam) | `wc` (wristcam)
- `task`: `pm` | `2sc` | `tsc` | `lp`
- `encoder`: `in1k` | `in1k-crop` | `r3m` | `dino-s-lora` | `dino-s-spatch` | `none` (Pi0.5 uses its built-in vision encoder)
- `scheme`: `cent` | `decent`
- `arm<N>`: only present for decent training rows (`arm0`, `arm1`, `arm2`); absent for centralized; absent for decent eval rows (eval fans out to all 3 arms)
- `phase`: `train` | `eval`
- `c<N>`: (eval only) train step of the ckpt being evaluated
- `seed`: `s<N>`
- `git7`: 7-char git short SHA of the launch commit

**Examples:**

- DP centralized PM workspace training: `dp_ws_pm_in1k_cent_train_s100_a3c736d`
- DP centralized PM workspace eval against ckpt 30000: `dp_ws_pm_in1k_cent_eval_c30000_s100_a3c736d`
- Pi0.5 decent TSC wristcam arm0 training: `pi05_wc_tsc_none_decent_arm0_train_s100_a3c736d`
- Pi0.5 decent TSC wristcam eval (uses all 3 arm ckpts at step 19999): `pi05_wc_tsc_none_decent_eval_c19999_s100_a3c736d`

### Resume = same wandb run (no new run on requeue)

The trainer must resume into the existing wandb run, not create a fresh one. Mechanism:

1. **First launch**: trainer calls `wandb.init(name=run_id, project=..., id=wandb.util.generate_id())` and writes the returned id to `<run_dir>/run_meta.yaml` field `wandb_run_id`.
2. **Resume launch** (orion preempt requeue, manual `scancel` + relaunch, or scheduled continuation): trainer reads `run_meta.yaml`, finds `wandb_run_id`, calls `wandb.init(id=wandb_run_id, resume="must")`. This continues logging into the same run; metrics append; the dashboard plot doesn't break.
3. **`run_meta.yaml` schema** (single source of truth for one logical run):
   ```yaml
   run_id: dp_ws_pm_in1k_cent_train_s100_a3c736d
   wandb_run_id: 1k7s9f2j           # set on first launch, never changes
   wandb_url: https://wandb.ai/...   # cached for convenience
   git_sha: a3c736d
   created_utc: 2026-05-04T14:30:00Z
   last_step: 12500                  # updated each ckpt-save
   final_step: null                  # set when training finishes cleanly
   resumed_count: 2                  # how many times this run has resumed
   ```
4. **Sanity guard**: if the launcher detects a `run_meta.yaml` with `final_step` already set and someone tries to launch the same `run_id` again, it refuses unless `--force-restart` is passed (prevents accidentally clobbering a finished run).

## Pre-flight checks — three distinct moments, three distinct purposes

Encoder collapse is one species of a bigger genus: **train/eval pipeline mismatch.** Your overfit-on-1-episode experiment proved this — you saw training loss drop to ~0 on a single episode, yet at eval the policy couldn't reproduce that same episode. That's not a learning problem; that's a *plumbing* problem. The image preprocessing differs, the action denormalization differs, the proprio normalization differs, the control rate differs, the init-pose distribution differs, or the camera intrinsics differ between the two pipelines. Encoder collapse is *one* manifestation; there are others.

To prevent the whole genus, the checks run at three different times:

### Stage 1: BEFORE training launches — Train/Eval Consistency Assertion Suite

Run once per `(model, dataset, task, scheme)` config the first time it's queued. **If it fails, training does not launch.** Catches the structural pipeline mismatch that overfit-replay surfaced.

This is a single Python script (`scripts/preflight/train_eval_consistency.py`) that loads the *training* dataloader and the *eval* env wrapper from the launcher's config and asserts:

1. **Image preprocessing parity**:
   - Same target resolution (`H × W`) and same channel order (`HWC` vs `CHW`).
   - Same normalization stats (mean/std per channel) — load the dataset's `image_stats.npz` and the eval wrapper's normalization config; assert byte-equal.
   - Same augmentation set at eval (typically: none) — confirm the eval pipeline does NOT apply train-only augs (random crop, color jitter).
2. **Action de/normalization parity**:
   - Compare `action_stats.npz` from the LeRobot dataset to whatever the eval wrapper uses to denormalize policy outputs.
   - Same action dimension and dtype.
   - For multi-arm: same per-arm split convention (decent must split the action vector identically in train and eval).
3. **Proprio (state) normalization parity**: same as actions, but for `state_stats.npz`.
4. **Control frequency parity**: training data was captured at `train_cfg.fps`; eval wrapper steps the env at `eval_cfg.fps`. Assert equal. (A 2× rate difference silently breaks rollouts.)
5. **Camera intrinsics/extrinsics**: training data has `camera_intrinsics.json` per camera; eval env loads its own. Assert intrinsics and extrinsics match within tolerance.
6. **Init-pose distribution**: take 50 training-data episode starts and 50 eval-env resets; compare empirical means/covariances of the joint-state distribution. Crash if KL divergence > threshold (catches "trained from one robot pose, evaluating from a different one").
7. **Overfit-replay sanity** (the strongest check, do this last): pick 1 training episode, run its actions open-loop through the eval env starting from the recorded init pose, render observations from the env, push observations through the *eval-side* preprocessing, then through the policy as if for inference. If the policy's predicted next-action diverges from the recorded action by more than ε (e.g. 0.1 in normalized action space), fail loudly. **If a freshly-overfit policy can't replay its own training episode at eval time, the pipelines are not compatible.**

The suite produces a single `<run_dir>/preflight_consistency.json` artifact. Manifest column `preflight_passed` records the result. Future LLMs / launchers refuse to start training if the artifact is missing or fails.

### Stage 2: AFTER training, BEFORE the first 60-seed eval — Encoder-Collapse Probe

Why: after Stage 1 passes (the pipeline is compatible), training can still produce a *broken* model — most commonly via the proprio-shortcut encoder collapse you documented for D1 TSC. `val_action_mse` will look great while eval SR is 0%.

How (concretely):

1. Pick 1 episode from the validation set; extract its `(image, proprio, action_chunk)` triple.
2. Compute **`mse_baseline`** = MSE between policy's predicted action chunk and the ground-truth chunk, with both `image` and `proprio` as normal inputs.
3. Compute **`mse_zero_image`** = MSE with the image input replaced by an all-zero tensor (proprio kept normal).
4. Compute **`mse_zero_proprio`** = MSE with proprio replaced by zeros (image kept normal).
5. Decision rule: flag collapse if `mse_zero_image / mse_baseline < 1.5` AND `mse_zero_proprio / mse_baseline > 5`. Tune as needed.
6. If flagged, mark `status=junked, category=junk, notes=collapse_detected` in manifest, skip the 60-seed eval entirely.

~3 forward passes per ckpt = ~10 seconds. Run before every eval, against every fresh ckpt.

### Stage 3: BEFORE every eval invocation — Per-eval guards

These run inside the `*_eval.sbatch` launcher itself, before any GPU is allocated:

- **Scene-match assertion**: trainer dumped `<run_dir>/.hydra_config.yaml`; eval reads it and asserts `train_cfg.task.env_runner.env_id == eval_cfg.task.env_runner.env_id` and the camera family matches (`*_workspace_*` vs `*_wristcam_*`). Crash on mismatch. (Concrete code in v1 of this plan; unchanged.)
- **Eval seed file frozen**: `sha256sum /iris/u/mikulrai/runs/eval_seeds_60.txt` matches pinned hash in `manifest.csv` header.
- **Wandb online**: `WANDB_MODE` and `WANDB_DISABLED` unset; `wandb status` shows correct user. Plus the **wandb fail-fast architecture** (next section) makes it impossible for a fresh eval driver to skip wandb at all.
- **GPU caps**: `squeue -u mikulrai -p iris-hi -t R,PD | wc -l` < 6 before submitting to iris-hi; route to orion otherwise.

### Why this stops both encoder collapse AND your overfit-mismatch issue

- The overfit-replay sanity in Stage 1 is the **strongest possible** train/eval-mismatch detector. If your "overfit one episode → can't replay it at eval" experiment failed, this suite would have flagged it before a single training step ran. **Bake this in once, never debug a pipeline mismatch the slow way again.**
- The encoder-collapse probe in Stage 2 catches the model-side failure that Stage 1 can't (the pipeline is fine; the model just learned a shortcut).
- The scene/wandb/seed guards in Stage 3 catch operational mistakes (wrong scene config, drifted seed file).

## Wandb fail-fast architecture (so this can't happen again)

**Root cause of the lost 30% TSC eval**: `/iris/u/mikulrai/projects/RoboFactory/robofactory/policy/openpi_pi05/eval_decent_pi05.py` has zero wandb integration — no import, no `wandb.init()`, no `wandb.log()`. The centralized counterpart `policy/Diffusion-Policy/eval_multi_dp.py` does have wandb (init at line 413, logs at 431/462). The decent driver was a fork that never got the wandb plumbing copied over. ~30 GPU-hours of eval compute went to a JSON nobody could find.

The **patch** is straightforward (one commit). The **architecture** that makes this class of mistake structurally impossible is what matters.

### The patch (Phase C, Commit 8)

1. Add `import wandb` near the top of `eval_decent_pi05.py`.
2. Add `--wandb` and `--wandb-tags` arguments to the `Args` dataclass (mirror `eval_multi_dp.py:101–104`).
3. In `main()`, before the eval loop: `wandb.init(project=..., name=run_id, tags=tags, config=args.__dict__)`.
4. After each episode: `wandb.log({"episode_idx": i, "success": int(succ), "steps": n_steps})`.
5. After eval finishes: `wandb.log({"success_rate": n_succ / n_total, "n_episodes": n_total})` then `wandb.finish()`.
6. Update `eval_pi05_decent_h100.sh` and any other launcher of `eval_decent_pi05.py` to pass `--wandb --wandb-tags 'eval,pi05,decent'`.

### The architecture (Phase C, Commit 8b — the part that prevents recurrence)

A future LLM (or a hurried human) writing a fresh `eval_<something>.py` should find it **structurally impossible** to skip wandb. Three layers:

1. **`BaseEvalDriver` class** in `src/openpi/eval/base.py`:
   ```python
   class BaseEvalDriver:
       def __init__(self, run_id, project, tags, config_dict):
           if os.environ.get("WANDB_MODE", "online") != "online":
               raise RuntimeError("WANDB_MODE must be unset or 'online'. Aborting.")
           if os.environ.get("WANDB_DISABLED"):
               raise RuntimeError("WANDB_DISABLED is set. Aborting.")
           self.wandb_run = wandb.init(name=run_id, project=project, tags=tags, config=config_dict)
           if self.wandb_run is None:
               raise RuntimeError("wandb.init() returned None. Aborting.")
           atexit.register(self._safe_finish)

       def log_episode(self, idx, success, n_steps, **extra): ...
       def log_summary(self, success_rate, n_episodes, **extra): ...
       def _safe_finish(self): ...
   ```
   The init refuses to construct without a live wandb run. No way to instantiate the driver and skip logging.

2. **All eval drivers must inherit from it.** `eval_dp.py`, `eval_multi_dp.py`, `eval_decent_pi05.py`, `eval_cent_pi05.py` (when written) — each is a thin subclass that overrides only the rollout loop. The wandb plumbing lives in the base class once.

3. **CI/lint check** in `pyproject.toml` or a tiny `scripts/lint/check_eval_drivers.py`: glob `**/eval_*.py`, parse the AST, assert each module's main eval class subclasses `BaseEvalDriver`. Fails CI/pre-commit if a new driver is added that doesn't inherit. Future LLM writes a from-scratch eval driver → CI red → forced to use the base class → wandb logging happens by construction.

4. **Launcher fail-fast at submit time** (defense in depth): `*_eval.sbatch` templates run a one-liner Python preamble that does `from openpi.eval.base import BaseEvalDriver; BaseEvalDriver._self_check()` before allocating GPU. The self-check verifies env vars, wandb auth, and project reachability. Fails crash the SLURM job before any compute is wasted.

After this, the only way to lose ~30 GPU-hours to "JSON on disk, nothing on wandb" is to disable all four layers — which would be a deliberate, visible act, not an accident a hurried fork can make.

## Dual ground truth — SR for me, rollout videos for you

The two of us verify policy quality through different channels and both should be on by default.

- **Success rate (60-seed eval)**: the scalar I can grep, sort, regress on across runs, and compare in the manifest. SR is what enters the ablation site, what gates the encoder-collapse probe, what `make manifest` exposes.
- **Rollout videos (per-episode)**: the perceptual channel only you can verify. An encoder-collapsed policy produces visually obvious "fishing" or "drift" behavior — a robot that moves without looking. You'd spot it in 30 seconds; I'd need 60 evals to detect it via SR distribution.

Architectural implication: the eval pipeline must always emit videos by default, not as an opt-in flag. Concretely:

- `BaseEvalDriver` records `rollout_video.mp4` per episode (or per failure case if disk is tight) into `<run_dir>/videos/`.
- Manifest gets a `videos_dir` column populated automatically.
- A small `scripts/inspect_run.sh <run_id>` opens the video directory + the wandb dashboard side-by-side for fast triage.
- The Phase B re-eval of suspected-junk TSC ckpts produces videos *first* — you can scan them in minutes and confirm collapse before I burn compute on the full 60-seed eval.

Don't trade videos for disk: if storage gets tight, downsample (1 fps, 256 px) before you delete.

## Prevention rules ("things to keep in mind")

1. **Each run's stdout, ckpt, eval, video lives in *one* per-run directory** keyed by the canonical `run_id`. Train run_ids have no step embedded (so resume = same dir = same wandb run). Eval run_ids embed `c<ckpt>` (so each eval is single-shot and traceable).
2. **Every ckpt that gets evaluated must register in the manifest** with its eval SR, scene config name, camera mapping, video path, and the full eval invocation. If it's not in the manifest, it didn't happen.
3. **Eval SR + rollout videos are the dual ground truth.** `val_action_mse` will lie when the encoder collapses. The Stage-1 train/eval consistency suite + Stage-2 encoder-collapse probe + visual scan of one rollout video gives you all three signals.
4. **Always run eval against the scene config the ckpt was trained on.** Scene-match assertion + camera-family assertion fail-fast in the launcher.
5. **Train/eval pipeline must be byte-identical-ish.** The Stage-1 consistency suite (image preprocessing, action denorm, proprio norm, control rate, camera intrinsics, init pose, overfit-replay sanity) runs once per `(model, dataset, task, scheme)` config before any training launches. **This is the structural fix for your overfit-mismatch problem** — it would have caught it before the experiment.
6. **No `WANDB_MODE=offline` ever.** Plus: the wandb fail-fast architecture (`BaseEvalDriver` + CI lint) makes it structurally impossible for a future eval driver to skip wandb. The `eval_decent_pi05.py` 30-GPU-hour lapse cannot recur.
7. **Resume = same wandb run.** Trainer reads `wandb_run_id` from `<run_dir>/run_meta.yaml` and calls `wandb.init(id=..., resume="must")`. No new run on requeue. No broken metric plots when orion preempts.
8. **Debug scripts are kept, but their output dirs must be parameterized** — no more hardcoded `/iris/u/mikulrai/logs/eval_bisection`. Default `--output_dir` to `/iris/u/mikulrai/scratch/<topic>_<date>/` (auto-deletable after 30 days).
9. **One parameterized launcher per pipeline, not one launcher per config.** `matrix.csv` is the source of truth; SLURM array indexes into it.
10. **One template config + factory, not N near-identical config registrations.** `make_robofactory_config(model, dataset, task, scheme, arm)` derives everything; per-(dataset, task, scheme, arm) configs go away.
11. **`logs/`, `slurm-*.out`, `wandb/`, `outputs/`, `multirun/` always gitignored.** Already done.
12. **Reorg and cleanup are separate commits.** Bulk-clean → ckpt-triage → reorg → infra-add — four phases, ~11 commits, each revertible.
13. **Bulk-delete only categorically-junk things (slurm stdout → distill, .bak, eval_bisection, failed-mid-training ckpts).** Best-of-breed candidates always human-gated.
14. **"Best of breed" is computed from manifest**, not memory — highest-SR-on-correct-scene-with-correct-camera; ties go to most recent mtime.
15. **Cent and decent are first-class in naming, manifest, factory configs, and launcher logic** — they don't get bolted on later.

## Phase C2 — Detailed Plan (2026-05-07, locked)

### Context

C1 organised the project (manifest, canonical/ablations split, Stage-3 launcher guards, eval_decent_pi05 wandb patch). C2 is the **structural firewall** preventing the recurring failure modes documented in C1: (a) end-to-end finetuning destroys the ImageNet encoder, val_action_mse stays low because of the proprio shortcut, eval is 0% (D1 + D2 confirmed); (b) ckpt path collisions silently overwrite training compute (Pi0.5 `v7fldf8d` lost ~14 GPU-hours of `fuktr1yw`'s ckpts); (c) eval drivers can be authored without wandb (eval_decent_pi05 lapse); (d) train/eval pipeline mismatch (overfit-replay surfaced this; SAPIEN/Vulkan render-distribution drift across nodes is the suspected hidden cause). Goal: PM 58.3% in1k reproduces end-to-end through the new pipeline as the binary go/no-go.

### Locked architectural decisions (Devil's Advocate critique applied)

1. **Eval drivers: procedural scripts + context managers**, not a class hierarchy. `WandbRun`, `VideoRecorder`, `EvalRunContext` are context managers; CI greps for `with WandbRun(...)` presence. Rationale: DP runs in-process, Pi0.5 spawns websocket servers — a `BaseEvalDriver` would leak server lifecycle into the base.
2. **Pi0.5 websocket servers stay** (3 per decent eval). C2 only cleans up wrappers, doesn't collapse to in-process inference. Server-collapse spike deferred.
3. **Encoder-collapse probe is metric-only** until ≥4 calibration ckpts exist (PM in1k 58.3%, D1 frozen-encoder retrains 15309191/192/193 once eval'd, Pi0.5 PM, one TSC freezeenc). Probe always logs `mse_baseline / mse_zero_image / mse_zero_proprio / feature_rank / per_channel_variance` to wandb; **does not block eval**. Hard gate added in a follow-up commit once calibration is in.
4. **Migration: read-side resolver** via `ckpt_index.jsonl`. No file moves on the existing 2 TB. New writes append a row + write to new path scheme. Lose index → regenerate by tree scan.
5. **Ckpt path keying: local `run_uuid` (uuid4)**, written to `run_uuid.txt`. `wandb_run_id` recorded separately inside the run dir, best-effort. Decouples training launches from wandb reachability on orion (preempt-heavy cluster).
6. **Default-on video → first-3-seeds-per-task only**, full video on `--video-all`. Disk math: 60 seeds × ~50 MB × N evals/wk = unsustainable on /iris.
7. **Init-pose check: per-dim Wasserstein with bootstrap CI**, not joint KL. Plus per-dim mean/std tolerance (0.5 cm / 0.5 deg). 50-sample joint KL on 7-D is noise-dominated.
8. **Vulkan render-distribution check** is its own preflight stage (Stage-1.5). Render same scene+seed on train node and eval node; assert per-channel mean/std within 2%. This is the "bug hiding behind every other check."
9. **Action-space-semantics assertion**: delta-vs-absolute, gripper convention 0/1 vs -1/1, joint vs eef. Round-trips cleanly through normalizer but breaks at `env.step`.
10. **Config factories deferred to post-C2.** Tidiness, not bug-prevention.

#### 3. Auto-tag wandb runs at `wandb.init()` time

The Tier-3 purge hand-tagged 9 wandb runs with `junk-encoder-collapse` after the fact. The `cent`/`decent`, `ws`/`wc`, `pm`/`tsc` tokens are all derivable from `run_id` at init time. One small function in `policy/_shared/eval_context.py:WandbRun.__init__`:

```python
def _derive_tags(run_name: str) -> list[str]:
    out = []
    for token in ("d1", "d2", "cent", "decent", "ws", "wc", "pm", "tsc", "lp", "in1k", "freezeenc"):
        if token in run_name.lower():
            out.append(token)
    return out
```

Then every future training/eval run is filterable from day one. ~30 LOC + a test. Compound benefit: when something fails 6 months from now, "show me all decent TSC runs" is one wandb URL away.
